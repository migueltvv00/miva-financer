<project_overview>
This is v1.7 of Fluxo, continuing from stable v1.6. Three parts:

1. FIX PAYSLIP PARSING — the parse-payslip Edge Function currently
   returns "Failed to extract payslip data" for all PDFs. Root cause:
   gemini-2.0-flash-lite (the model in use) does not reliably support
   PDF inline_data multimodal input. Fix the model choice and add
   proper diagnostics so the error is never a black box again.

2. GEMINI USAGE TRACKER — the user has no visibility into how many
   Gemini API requests have been used today vs the daily limit. Track
   every Gemini call in a DB table, expose the usage in the Settings
   debug panel, and add a /quota Telegram command.

3. PAYMENT METHOD TAGGING — allow transactions to be tagged with the
   payment method used (cartão de refeição, Multibanco, MBWay, etc.).
   This is especially useful for separating meal-card spending from
   personal spending. Expose in both the web UI and the Telegram bot.

Stable from v1.0–v1.6 — do not touch existing features unless
strictly required by the above.
</project_overview>

<tech_stack>
Defined in copilot-instructions.md. No new libraries this version.

GEMINI MODEL STRATEGY (two different models, two different jobs):

1. Text/NLP tasks (Telegram bot NL parsing): gemini-2.0-flash-lite
   — fast, cheap, text-only, already working.

2. Multimodal/PDF tasks (payslip parsing): gemini-1.5-flash
   — proven multimodal support, handles PDF inline_data reliably.
   The lite variant lacks full multimodal capabilities.

Model constants: define two named constants instead of one, both
in a shared config at the top of each Edge Function:
  GEMINI_TEXT_MODEL  = "gemini-2.0-flash-lite"
  GEMINI_PDF_MODEL   = "gemini-1.5-flash"

Rate limits reference (free tier):
  gemini-2.0-flash-lite: 30 RPM, 1500 RPD, 1M TPM
  gemini-1.5-flash:      15 RPM, 1500 RPD, 1M TPM

PDF via Gemini 1.5 Flash — use the REST inline_data pattern:
  POST https://generativelanguage.googleapis.com/v1beta/models/gemini-1.5-flash:generateContent?key={KEY}
  Body:
  {
    "contents": [{
      "parts": [
        { "inline_data": { "mime_type": "application/pdf", "data": "{base64}" } },
        { "text": "{prompt}" }
      ]
    }],
    "generationConfig": { "responseMimeType": "application/json" }
  }
Use context7 to verify the exact REST API pattern for gemini-1.5-flash
before implementing. Do not assume it is identical to prior versions.
</tech_stack>

<debugging_guide>
--- HOW TO DEBUG TELEGRAM BOT RESPONSES ---

This section is for the developer to understand how to investigate
issues without writing any new code.

1. SUPABASE EDGE FUNCTION LOGS (primary source of truth)
   Go to: https://supabase.com/dashboard/project/mkihzxyplnfktsicsrpw/functions
   Click "telegram-webhook" → "Logs" tab.
   Each request produces structured JSON lines (see logging_standards
   from v1.5). Filter by op field to isolate a specific operation.
   The log will show: Gemini call status, raw error from the API,
   DB query results, PIN validation outcome.
   ⚠️  The "API" tab only shows HTTP metadata (status, URL). The
   actual console.log output is only in the "Logs" tab.

2. SIMULATE A TELEGRAM MESSAGE WITH CURL
   The webhook accepts the same JSON Telegram would send:
   ```
   curl -X POST https://mkihzxyplnfktsicsrpw.supabase.co/functions/v1/telegram-webhook \
     -H "Content-Type: application/json" \
     -d '{
       "message": {
         "message_id": 1,
         "chat": { "id": YOUR_CHAT_ID, "type": "private" },
         "from": { "id": YOUR_CHAT_ID, "username": "yourname" },
         "text": "/start",
         "date": 1700000000
       }
     }'
   ```
   Replace YOUR_CHAT_ID with 8966723125.
   You can use any message text to test NL parsing.
   The response body is what the Edge Function returned, not what
   Telegram shows — it is the raw bot reply before Telegram formats it.

3. THE /debug TELEGRAM COMMAND (if implemented)
   Send /debug to the bot. It returns a JSON dump of your current
   session state from telegram_sessions (authorized, username,
   linked_at, digest_enabled).

4. THE DEBUG PANEL IN SETTINGS (web)
   Settings → Telegram → Debug panel (collapsible at the bottom).
   Shows client-side log entries generated by the frontend during
   PIN generation and status polling. Does NOT show Edge Function logs.
   Use together with Supabase logs, not instead of.

5. CHECK THE GEMINI API RESPONSE DIRECTLY
   If parse-payslip fails, the error is in the Supabase logs.
   Look for a log entry with op="gemini" and status="error".
   The "error_preview" field contains the first 500 chars of the
   raw Gemini error body — this tells you exactly why it failed
   (quota exceeded, unsupported model, invalid MIME type, etc.).

6. VERIFY BOT WEBHOOK IS REGISTERED
   ```
   curl https://api.telegram.org/bot{TOKEN}/getWebhookInfo
   ```
   Response shows: url, pending_update_count, last_error_message.
   If last_error_message is non-empty, Telegram is having trouble
   reaching the Edge Function.
</debugging_guide>

<architecture_decisions>

--- PART A: FIX PAYSLIP PARSING ---

Root cause diagnosis (do this first, before any code changes):
1. Check Supabase logs for the parse-payslip function.
   Find the log entry with op="gemini" status="error".
   Read the error_preview field — it will contain the exact
   Gemini API error message and HTTP status code.
   Document the finding in the PR description.

2. The most likely cause: gemini-2.0-flash-lite does not accept
   application/pdf in inline_data. Gemini API returns 400 with
   "Request contains an invalid argument" or similar.

Fix:
1. In parse-payslip/index.ts: change the GEMINI_MODEL constant
   to "gemini-1.5-flash" (dedicated constant GEMINI_PDF_MODEL).
   Update the fetch URL accordingly.

2. Improve the error response: when Gemini returns non-200,
   include the HTTP status code and a truncated error preview in
   the response body so the frontend can show a more specific
   error message. Current code hides all detail behind a generic
   "Failed to extract payslip data".
   New error response shape:
   { error: "Gemini extraction failed", geminiStatus: number,
     detail: string (first 200 chars of Gemini error body) }
   Frontend should display: "Gemini returned {status}: {detail}"
   in the upload error state instead of the generic message.

3. Update PayslipImport.tsx to render the new detailed error
   when present.

4. Add a pre-call model validation: log the model name at every
   Gemini call start so it is always visible in logs.

Verification gate for Part A:
- Upload a real Portuguese payslip PDF.
- Supabase logs show op="gemini" status="ok" with model=gemini-1.5-flash.
- Frontend shows the review screen with extracted values.
- Do not proceed to Part B until this passes.

--- PART B: GEMINI USAGE TRACKER ---

New Supabase table:
gemini_usage:
  id            uuid pk default gen_random_uuid()
  user_id       uuid references auth.users not null
  model         text not null
  fn_name       text not null       -- Edge Function name
  date          date not null       -- UTC date of the call
  tokens_in     integer default 0
  tokens_out    integer default 0
  created_at    timestamptz default now()
  -- One row per individual API call (not aggregated)

Index: CREATE INDEX ON gemini_usage (user_id, date);
RLS: auth.uid() = user_id on SELECT. No direct client INSERT/UPDATE.

Usage counting strategy:
- After every successful Gemini API call in any Edge Function
  (telegram-webhook, parse-payslip), insert a row into gemini_usage
  using the SERVICE_ROLE_KEY client (bypasses RLS for the insert).
- Extract token counts from the Gemini response:
  response.usageMetadata.promptTokenCount  → tokens_in
  response.usageMetadata.candidatesTokenCount → tokens_out
  If usageMetadata is absent: store 0 (do not fail the main flow).
- This insert must be fire-and-forget: wrap in try/catch, never
  let a tracking failure affect the main operation.

New Edge Function: GET /functions/v1/gemini-quota
Auth: requires valid user JWT.
Returns:
{
  today: {
    date: "YYYY-MM-DD",
    requests: number,
    tokens_in: number,
    tokens_out: number
  },
  last7days: [
    { date: "YYYY-MM-DD", requests: number, tokens: number }
  ],
  limits: {
    text_model: { name: string, rpm: number, rpd: number },
    pdf_model:  { name: string, rpm: number, rpd: number }
  }
}
Implementation: single SQL query grouped by date, last 7 rows,
ordered DESC. Return limits as hardcoded constants.

Frontend — Settings debug panel extension:
Extend the existing TelegramDebugPanel (or add a sibling
GeminiQuotaPanel component) in Settings:

Section title: "Uso Gemini"
Content:
  Hoje: {N} pedidos  /  {tokens_in + tokens_out} tokens
  Limite diário: 1500 pedidos (modelos: gemini-2.0-flash-lite,
                                        gemini-1.5-flash)
  Mini gráfico de barras (7 dias): sparkline using existing
  Recharts dependency — BarChart with 7 bars, x=date label
  (e.g., "Seg", "Ter"), y=request count.
  If today's requests ≥ 1350 (90% of limit): show yellow warning.
  If today's requests ≥ 1500: show red warning "Limite atingido".

Fetch on mount (not realtime). Manual refresh button.
Show loading skeleton while fetching.
Show error state if gemini-quota returns non-200.

Telegram /quota command:
Handle /quota in telegram-webhook.
Call gemini-quota Edge Function internally (service role, no JWT
overhead needed since we're already server-side — query the DB
directly from the webhook handler).
Reply message format:
  📊 *Uso Gemini hoje*
  Pedidos: {N} / 1500
  Tokens: {total}
  [Barra de progresso visual: ████░░░░░░]
  Modelos: gemini-2.0-flash-lite · gemini-1.5-flash
  _Actualizado: {HH:MM}_

Helper function for the progress bar:
  progressBar(used, total, width=10) → "████░░░░░░"
  filled = Math.round((used/total) * width), rest = width - filled
  "█".repeat(filled) + "░".repeat(rest)

--- PART C: PAYMENT METHOD TAGGING ---

New column on transactions table:
  ALTER TABLE transactions ADD COLUMN payment_method text;
  CHECK constraint: payment_method IN (
    'cartao_refeicao', 'multibanco', 'mbway',
    'numerario', 'credito', 'debito'
  ) OR payment_method IS NULL
Default: NULL (no method recorded = unspecified).

Display labels and icons (use emoji, no icon library):
  cartao_refeicao → 🍽️ Cartão Refeição
  multibanco      → 🏧 Multibanco
  mbway           → 📱 MBWay
  numerario       → 💵 Numerário
  credito         → 💳 Crédito
  debito          → 💳 Débito
  null            → (nothing shown)

Transaction list: if payment_method is set, show the emoji
in small muted text below the transaction note (or inline).
Do not take up a new row — keep it compact.

Transaction entry (NumPad / AI flow):
After the user confirms amount + category, show a small optional
"Como pagaste?" selector row with the 6 method buttons
(emoji + short label). "Saltar" link at the end.
Default: no selection (null). Tapping a method highlights it.
The selection is not required — skipping leaves it null.
Persist last-used payment method in localStorage under
'fluxo-last-payment-method' and pre-select it on the next entry.

Edit transaction modal: add the same payment method selector.

Telegram NL parsing:
Add payment_method extraction to the Gemini prompt for NL parsing.
Extend the JSON schema expected from Gemini with:
  "payment_method": "cartao_refeicao" | "multibanco" | "mbway" |
                    "numerario" | "credito" | "debito" | null

Prompt addition (append to existing NL prompt):
  "payment_method: extract if the user mentions how they paid.
   Examples: 'cartão de refeição' → cartao_refeicao,
   'multibanco' or 'MB' → multibanco, 'MBWay' → mbway,
   'dinheiro' or 'numerário' → numerario,
   'crédito' → credito, 'débito' → debito.
   Return null if not mentioned."

When Telegram bot creates a transaction and payment_method
is extracted: include it in the confirmation reply:
  "✅ Despesa · €12,50 · Alimentação · 🍽️ Cartão Refeição"

If the user sends a Telegram transaction without specifying
payment method, bot asks "Como pagaste?" with inline keyboard
buttons (the 6 methods + "Não especificar"). This is optional —
only ask if payment_method is null AND the transaction type is
expense (income rarely has a payment method).

Transaction filter UI:
Add "Método de pagamento" as a filter chip in the transaction
list filter row. Multi-select allowed. Chips: one per method
(emoji + label). "Todos" clears the filter.

Summary widget (optional, only if time allows):
In the dashboard or transaction list header, when filter is active,
show total filtered. No new screen needed.

<future_features>
Suggestions for v1.8 and beyond — not in scope for this version.
Document in Jira as separate epics.

HIGH VALUE:
- CSV bank statement import (CGD, BPI, BCP, Santander PT format)
  The user's bank exports transactions as CSV. Parse and bulk-import.
  Deduplication by date+amount+description.
- IRS annual estimator
  Based on payslip YTD income, project the annual taxable income
  and estimate the IRS refund/payment using the Portuguese IRS tables.
  Single-page view, no external API needed.
- Export transactions to CSV/PDF
  One-click export for any date range. Essential for accountant use.

MEDIUM VALUE:
- Budget rollover
  Unused budget in a category rolls to the next month.
  User opt-in per category.
- Bill tracker
  Recurring fixed-date expenses (renda, seguro, ginásio).
  Dashboard card showing "próximas saídas" for the next 30 days.
- Split transaction
  Divide one transaction across two or more categories.
  E.g., supermarket receipt: 60% Alimentação, 40% Casa.
- Tags / labels
  Free-text tags on transactions (e.g., "reembolsável", "trabalho").
  Filter and summarise by tag.

LOWER VALUE:
- Multi-currency support (for travel)
- Savings goals with progress bar
- Shared budgets (multiple users)
</future_features>
